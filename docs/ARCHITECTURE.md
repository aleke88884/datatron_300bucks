# Архитектура решения и используемые модели

Кейс ForteBank (Datathon 26): локальный веб-сервис + API, который по `.mov`-записи кассы выдаёт вердикт
`violation` / `no_violation`, список событий с таймкодом, кадрами-доказательствами и ссылкой на пункт
нормативного акта РК. Этот документ — описание архитектуры и моделей (раздел 8 ТЗ).

Актуальный код: `service/` (пайплайн `service/pipeline/`, API `service/app/`, UI `service/static/`), ветка `release/final`.
Итог на 42 обучающих роликах (`service/results/eval.txt`): **TP 17 / FN 5 / FP 0 / TN 20** — точность 88 %, полнота 77 %,
precision 100 %; таймкод: медиана ошибки 0.6 с, 15 из 17 найденных в допуске ≤ 3 с. Пороги подбирались на этих же 42
роликах, отложенной выборки нет (см. `LIMITATIONS.md`).

## 1. Принцип: структурный пайплайн + правила, VLM — не судья

Мы сознательно **не** отдаём видео мультимодальной модели с вопросом «есть ли нарушение?». Такой подход даёт
шумные вердикты, неточные таймкоды и выдуманные ссылки на нормативку, а ТЗ штрафует и ложные срабатывания,
и пропуски. Вместо этого нарушение определяется **состоянием объектов сцены в момент события** (сейф открыт?
деньги на столе? экран активен? кто в помещении? открыта ли дверь?), а таймкод — это **момент перехода состояния**
(начало нарушающего действия, как в разметке датасета).

```
                          ┌─ детектор людей/предметов YOLOX-m (3 к/с) ─┐
.mov ─▶ [1] Восприятие ───┼─ поза рук RTMPose-m (по рамкам YOLOX)      ├─▶ [2] Сцена: роли, зоны,
        (ONNX Runtime,    ├─ детектор купюр «под цвет стола» (cash)    │    самокалибровка камеры,
         CPU)             └─ область двери по движению створки (door)  ┘    таблица состояний 2 к/с
                                                                                │
   JSON + кадры с рамкой ◀── [3] Правила T1–T13: машина состояний ◀─────────────┘
   + пункт НПА РК + таймлайн     (таймкод = переход состояния; уточнение момента — timing.py)
                │
                └─▶ [4] Опционально: локальная VLM — описание событий и страховочная сетка для неизвестных типов
```

Весь живой путь (`analyze_video` без `FEATURES_CACHE`) считает признаки по самому видео. Путь через кеш
(`FEATURES_CACHE=service/results`, `scripts/eval_rules.py`, тесты) читает те же признаки из числовых JSON
(`results/perception|states|cash|door|hands|timing|personal_items|safety_net/*.json`; кадров и видео в них нет) и
нужен только для быстрой офлайн-оценки. Живой путь сверен с кешем на Х-14, Х-22, Х-29 (вердикты совпали), а Х-32, Х-40, Х-46 прогонялись вживую отдельными треками с теми же результатами.

### Слой 1. Восприятие

- Декодирование `.mov` — OpenCV (FFmpeg внутри колеса `opencv-python-headless`), `pipeline/video.py`. Кадры-доказательства
  читаются одним последовательным проходом (`read_frames_at`): прежний seek по времени давал кадры на 2–7 с позже
  на 7 из 42 роликов. Отдельно строится ряд средней яркости на 10 к/с (T9 «свет выключен», T3 в темноте).
- **Детектор людей и объектов — YOLOX-m** (COCO, 80 классов), ONNX Runtime, `pipeline/detect.py`, вход 640×640
  letterbox, 3 к/с. Используем классы `person`, `handbag`/`backpack`/`suitcase`, `cup`/`bottle`/`wine glass` и еду,
  `cell phone`, `laptop`, `chair`, `dining table`. Провайдер — `ORT_PROVIDERS` (CPU по умолчанию, CUDA в `deploy/Dockerfile.gpu`).
- **Треки и «внутри кассы»** — `pipeline/perception.py`: сопоставление рамок между кадрами, низ рамки относительно
  порога двери и матовой полосы стекла, гистерезис.
- **Состояния сцены** — `pipeline/states.py`: якоря (стол, сейф, ноутбук, дверь), экран (активен / заблокирован /
  выключен), зелёная инкассаторская сумка, предметы на столешнице.
- **Купюры «под цвет стола»** — `pipeline/cashdetect.py` (история — `MIMICRY.md`): пачки 5000 тг по цвету совпадают с деревом
  стола, поэтому ищутся не по цвету, а по контрасту яркости и насыщенности относительно статистики самого стола в том же
  кадре, после баланса белого по белым стенам; люди маскируются, неподвижный объект «помнится», пока его закрывает тело.
- **Дверь кассы** — `pipeline/door.py`: область двери находится сама как крупнейшая движущаяся вне рамок людей область у
  входа/выхода; дальше ряд «доля области, отличной от вида до первого открывания» (4 к/с) и проходы людей через проём.
- **Поза рук** — `pipeline/pose.py`: **RTMPose-m (body7)**, ONNX Runtime, 17 точек, top-down по рамкам YOLOX (отдельный
  детектор не нужен), 3 к/с, порядка 13 с на видео в 143 с. Признаки только относительные: положение кисти в системе
  плеч кассира, «поза покоя» — медиана по самому ролику; точка с уверенностью < 0.3 считается «неизвестно». Хранятся
  только координаты суставов; лица не распознаются. Слой пропускается, если до мягкого дедлайна осталось < 20 с.
- Если весов детектора нет, пайплайн не падает: работают правила по яркости (T9-контекст, T3 в темноте), причина — в
  `meta.perception_error`. Сбой cash/door/pose/camera/timeline не роняет анализ: поле остаётся пустым, правила молчат.

### Слой 2. Сцена и состояния (по секундам) — `pipeline/scene.py`

Роли и зоны строятся **от детекций, а не от пиксельных координат** — это основа устойчивости к другому ракурсу
(критерий 5):

- **Кассир** — самый долгий уверенный трек у стола. **Посетители** — остальные уверенные треки внутри кассы
  (клиент в зоне обслуживания, третий человек — посторонний). **Фантомы** — слабые/мелкие детекции (люди за
  стеклом, отражения) — в подсчётах не участвуют.
- **Рабочая зона** = сторона стола, где находится кассир; зона сейфа = якорь сейфа; дверь = полоса двери.
- Таблица состояний на сетке 2 к/с: `cashier_inside`, `cashier_at_desk`, `cashier_near_safe`, `n_inside`,
  посетители внутри / в рабочей зоне, предметы на столе (купюры, зелёная сумка, напиток), экран активен,
  дверца сейфа, свет.
- Минимальная длительность состояния (1–2 с, константы `*_SEC` в `rules_scene.py`) и гистерезис — защита от
  дрожания детекций.

**Самокалибровка под камеру ролика — `pipeline/camera.py`** (вызывается в `analyze_video` перед построением
сцены, работает и на живом пути, и на кеше признаков):

- **Масштаб сцены.** Пороги в пикселях (площадь предмета на столе, сумки, отступы зоны стола, минимальный рост
  «настоящего» человека) заданы в пикселях эталонного кадра 464×848 и умножаются на масштаб: H/848 для этой
  камеры, по росту людей в кадре (75-й перцентиль высот уверенных рамок) — если он расходится с H/848 вне
  диапазона ×0.5–1.4 (другое разрешение, приближение, альбомный кадр).
- **Экспозиция.** Цветовые маски (дерево стола, зелёная сумка, серый сейф) и пороги яркости экрана (активен /
  заблокирован, светится в темноте) приводятся к эталонной экспозиции: коэффициент = 137.5 / средняя яркость
  кадра без чёрных полей; в пределах разброса обучающих роликов (×0.85–1.18) коррекции нет.
- **Тест «внутри кассы» без координат двери.** Люди за стеклом стоят дальше стола: низ их рамки выше центра
  столешницы более чем на 0.7 роста человека в кадре; у людей внутри — ниже 0.45 роста (между порогами —
  крупная фигура считается внутри, иначе состояние наследуется по треку). Откалиброванная геометрия этой камеры
  (`SceneGeometry`) остаётся, только если согласуется с этим тестом (расхождение ≤ 5 % уверенных наблюдений;
  на 42 роликах датасета в сумме 11 из 8006, максимум 4 %); иначе (зеркальный кадр, другой ракурс) используется
  относительный тест. На 42 роликах офлайн-оценка в принудительном относительном режиме: те же TP 11 / FP 0.
- **Обрывки трека кассира.** Короткий (≤ 3 с) трек «посетителя», который обрывается/начинается в точке, где через
  ≤ 2 с появляется/исчезает кассир, присоединяется к кассиру (при повороте кадра детектор чаще теряет человека).
  Режим и коэффициенты видны в `meta.scene.camera`; переключатель `CAMERA_INSIDE=auto|fixed|relative`.
- Проверка: `scripts/robustness.py` прогоняет живой пайплайн на преобразованных вариантах видео (отражение,
  повороты ±15–20°, перспектива, приближение, экспозиция, альбомный кадр 1280×720), таблица — `results/robustness.md`.

### Слой 3. Правила — машина состояний T1–T13

Правила: `pipeline/rules_scene.py` (T1, T2, T4–T8, T10, T13 на таблице состояний), `pipeline/rules_door.py` (T13
по состоянию двери), `pipeline/rules_hands.py` (T6 по позе), `pipeline/personal_items.py` (T8), `pipeline/detectors.py`
(список `DETECTORS`, T9 и T3 в темноте по яркости). Событие = переход состояния; `timecode_sec` = начало нарушающего
действия. `pipeline/timing.py` уточняет момент: T1 — кассир уходит с последнего места работы, T4 — вошедший дошёл до
места, где остаётся, T8 — предмет впервые появился на столе (перепроверка кропа стола на 5 к/с). Для каждого события —
1–3 кадра с рамкой и подписью (`pipeline/draw.py`). `pipeline/timeline.py` строит дорожки состояний сцены для UI
(`meta.timeline`; неизвестное состояние рисуется штриховкой, а не как «закрыто/выключено»).

Правила делятся на две фазы: **контекстные** (`CONTEXT_ONLY_TYPES = {"T9"}`) не дают вердикта и пишутся в
`meta.context_events`; **правила-нарушения** дают события и вердикт. Политика вердикта: `violation`, если есть хотя бы
одно событие с `confidence >= 0.5` (`MIN_CONFIDENCE`); третьего вердикта нет (ТЗ). При неизвестном состоянии (перекрытие,
темнота, якорь не найден) правило молчит: сомнение — в пользу `no_violation`. Справочник типов, признаков и пунктов —
`pipeline/rules.py` (`RULES_SOURCES.md`, `VIOLATION_TYPES.md`).

| Реализованы и дают события | Включено флагом / вне вердикта | Выключены / не реализованы |
|---|---|---|
| T1 (ценности на столе + уход кассира), T3 (экран активен + уход; светится в темноте), T4 (посторонний), T5 (клиент в рабочей зоне), T6 (клиент встал и ушёл, кассир продолжает работать руками — по позе), T7 (купюры на столе при входе нового человека), T8 (напиток/еда на столе; сумка в руках кассира), T10 (инкассаторская сумка внутри), T13 (дверь кассы открыта ≥ 6 с) | T9 — контекст, вердикт не даёт; T11 — признак «купюры к карману» помечен как индикатор, но не выдаётся; S1 страховочной сетки (T4) — всегда включён, на 42 роликах не срабатывает | **T2** (`T2_ENABLED=False`): сейф оставлен открытым — не отделяется от «кассир стоит у сейфа», в Х-22 дверца вообще не открывается (оставлен ключ в замке, ~4×3 пикс.). **T11, T12** — не реализованы: «руки у груди» одинаковы в нарушении и в чистых, движения «в карман» по кадрам не видно |

Состояние по 42 роликам (`scripts/eval_rules.py`, 18.10.2026): **TP 17 / FN 5 / FP 0 / TN 20**. Пропущены Х-1, Х-2, Х-44
(наличные в карман/в руке) и Х-20, Х-22 (сейф) — `LIMITATIONS.md` §2. Ход по ветвям (TP/FP): базовая 11/0 → cash 14/0 (Х-4, Х-26, Х-47) →
door 15/0 (Х-32) → items 16/0 (Х-40) → hands 17/0 (Х-34).

### Слой 4. VLM — только описание и страховка (опционально, локально) — `pipeline/vlm.py`

Локальная мультимодальная модель используется **не для вердикта**; слой необязателен и по умолчанию на 8 ГБ ОЗУ отключён
(7B непригодна, 2B-вариант — только при поднятом `llama-server`).
- (а) **описание** (подключено, включается `VLM_ENABLED=1`): по 1–3 кадрам уже найденного события модель
  переписывает шаблон правила в 2–3 предложения «что видно на кадрах». Хук — в `analyze_video` на стадии
  `describing`. Модель не меняет тип, таймкод, уверенность и вердикт; шаблон сохраняется в `description_template`;
  юридические выводы («похитил», «мошенничество») и описания внешности людей отбраковываются постобработкой.
  Лимиты: `VLM_MAX_EVENTS=5`, `VLM_BUDGET_SEC=60`, `VLM_TIMEOUT_SEC=20` — VLM добавляет к видео не более ~60 с,
  лимит ТЗ в 5 минут не нарушается. При любой ошибке/таймауте остаётся шаблон; пайплайн из-за VLM не падает.
- (б) **страховочная сетка от неизвестных типов (FAQ 9)** — `pipeline/safety_net.py`, запускается только когда
  правила ничего не нашли. Принцип «детектор предлагает, VLM подтверждает, контроль опровергает»; модель не просматривает
  видео целиком и не выбирает тип или пункт закона.
  - **S1, структурный, без VLM, всегда включён:** посетитель ≥ 3 с остаётся один после ухода кассира, с которым был
    внутри → T4. На 42 обучающих роликах не срабатывает.
  - **Предметные пробы (телефон, напиток/еда, личная сумка), нужна VLM:** Qwen3-VL-2B (llama.cpp, GGUF Q4) отвечает «да/нет»
    по увеличенному кропу; нужны «да» на ≥ 2 кадрах через ≥ 1 с, «нет» на опровержениях и в контрольный момент. Тип и
    пункт берутся из `RULES` (T8, п. 12), описание — фиксированный шаблон «требует проверки человеком», `source: "safety_net"`.
  - **Когда работает:** `SAFETY_NET=auto` — только если VLM включена (`VLM_ENABLED=1 VLM_BACKEND=llamacpp`) и проходит замер
    скорости (≤ 8 с на ответ); бюджет 45 с, не больше остатка до жёсткого дедлайна минус 60 с.
  - **Измерено:** на 20 чистых — 0 срабатываний; на финальной ветке Х-40 уже находит правило T8, поэтому с сеткой и кешем
    ответов итог прежний (17/0). Сетка не является источником баллов на обучающей выборке — это страховка.
  - **Честно:** на целевой машине с 8 ГБ ОЗУ предметные пробы выключены (VLM не поднимается), в демонстрации работает только S1.
    Модель 2B не отличает телефон от купюр на кадре 464×848 (пример: в Х-1 веер купюр принят за стакан — закрыто требованием
    ≥ 3 детекций за ≥ 1 с). Если ворота `scripts/eval_safetynet.py` на хосте не пройдены, держать `SAFETY_NET=0`.

Без VLM (`VLM_ENABLED=0`, по умолчанию) сервис работает как прежде — описания шаблонные, они же — формулировки из
`RULES_SOURCES.md` (наблюдаемые факты, без юридических выводов). Установка: `requirements-vlm.txt`,
`scripts/get_vlm.py` (7B ~16 ГБ) или `scripts/get_vlm.py --gguf` (2B ~1.5 ГБ); подробности — `service/README.md`.

## 2. Модели и лицензии

Все модели открытые, с лицензиями, допускающими коммерческое использование. После скачивания весов интернет не нужен.

|---|---|---|---|

Что **не** используем и почему:
- **Ultralytics YOLO (v5/v8/v11) — AGPL-3.0**: для коммерческого продукта банка потребовала бы раскрытия кода или платной лицензии. Взят YOLOX.
- **Qwen2.5-VL-3B-Instruct — Qwen Research License** (некоммерческая): только 7B (Apache-2.0); `get_vlm.py` отказывается качать 3B.
- **RTMDet** — на агрегаторах лицензия указана как GPL-3.0, репозиторий MMDetection — Apache-2.0; веса RTMDet не используем.
- **Распознавание и идентификация лиц — не используем** (FAQ кейса п. 29). Роли определяются по положению и трекам, а не по
  внешности; детектора лиц нет; поза хранит только координаты суставов.
- Облачные LLM/VLM/API — не используем; единственный сетевой вызов кода — к локальному `llama-server` (`VLM_SERVER_URL`).

## 3. Локальность и переносимость

- **Локальность.** Сервис — один процесс FastAPI + пул воркер-процессов с пайплайном. Никаких внешних вызовов.
  Контейнер проверен с `--network none` (`tests/test_docker.py`). Загруженное видео удаляется сразу после
  анализа (`KEEP_UPLOADS=false` по умолчанию); результаты заданий хранятся только в памяти процесса API.
- **Переносимость.** Зависимости — `requirements.txt` (Python 3.12, OpenCV headless, ONNX Runtime, Pillow).
  Проверен запуск на macOS (Apple Silicon, CPU) и Windows 11 (CPU; `scripts/run_all.ps1` — 9 шагов: Python →
  venv → веса → датасет → признаки → `eval_rules` → pytest → VLM при `WITH_VLM=1` → push). Docker-образ
  `python:3.12-slim` (CPU; веса YOLOX скачиваются на этапе сборки, контейнер работает без интернета) и
  `deploy/Dockerfile.gpu` (NVIDIA CUDA, `onnxruntime-gpu`, опционально VLM). Системный ffmpeg не нужен.
- **Публичный URL** для жюри — туннель к локальному сервису (`deploy/cloudflared.md`) или арендованный GPU-сервер
  с `docker compose`. Туннель только проксирует HTTP; обработка видео остаётся на нашей машине.

## 4. Производительность, лимит 5 минут

- ТЗ: ≤ 5 минут на видео. Часы идут **с момента POST**. `pipeline/budget.py`: мягкий дедлайн 168 с (70 %), жёсткий 240 с
  (`JOB_TIMEOUT_SEC`). После нескольких кадров `StrideGovernor` оценивает скорость и при нехватке времени увеличивает шаг
  выборки (3 → 1.5 → 1 к/с), в крайнем случае обрезает этап; при опоздании кадры-доказательства берутся по одному на
  событие, поза и VLM пропускаются. На жёстком дедлайне клиент получает `done` с последним готовым результатом (или
  безопасным `no_violation` с `meta.degraded=true`, `meta.fallback=true`), а не `failed`. `failed` — только для файла,
  который нельзя декодировать.
- Воркеры: пул из `WORKERS` процессов (по умолчанию 2 при ≥ 4 ядрах, каждый со своими потоками ORT), прогрев при старте.
- Замеры живого пути (`service/results/live_check.json`; 8-ядерный M3, 8 ГБ ОЗУ, без кеша): Х-14 (142.5 с) — 143.6 с на всех
  ядрах без дедлайнов (детектор+состояния 125 с, поза ≈ 13 с, правила и кадры ≈ 13 с) и **89 с в производственных настройках**
  (4 потока ORT при `WORKERS=2`; бюджет удвоил шаг выборки, `degraded=true`, вердикт тот же); Х-22 (≈ 20 с) — 22 с; Х-29 — 24 с.
  Офлайн-оценка по кешу — 31 с на все 42 ролика.
- Честно: в деградированном режиме полнота на длинных видео ниже; на `WORKERS=1` очередь из нескольких видео не уложилась бы в
  дедлайны. 308 тестов проходят (в т. ч. e2e с живым сервером; 3 пропущены — нет Docker-демона, 1 ожидаемый xfail).
- VLM-слой (если включён) — не более `VLM_BUDGET_SEC=60` с на видео; страховочная сетка — 45 с.

## 5. Сервис и API

- `service/app/main.py` — FastAPI; `X-API-Key` на всех `/api/v1/*` (401 без/с неверным ключом); `/health` без ключа.
- `service/app/worker.py` — очередь и пул из `WORKERS` дочерних процессов (`multiprocessing`, spawn), модели загружаются
  один раз в `pipeline.warmup()`; жёсткий дедлайн убивает процесс, но клиент всё равно получает ответ.
- `service/static/index.html` — одна страница: загрузка → статус по стадиям → вердикт → плеер с таймлайном и дорожками
  состояний сцены → события с кадрами, описанием, документом + пунктом + дословной цитатой + ссылкой на adilet,
  контекст сцены, «Скачать JSON».

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/analyze` | multipart-поле `file` (.mov, до 300 МБ) → `{"job_id": "..."}` (HTTP 200) |
| GET | `/api/v1/jobs/{job_id}` | статус `processing` / `done` / `failed` и результат |
| GET | `/api/v1/rules` | справочник типов нарушений и нормативных пунктов |
| GET | `/health` | без ключа; состояние воркера и очереди |

Поля ТЗ: `job_id`, `status`, `verdict`, `violations[] {type, timecode_sec, description, evidence_frames[] {timestamp_sec, image_base64}}`.
Расширения (не ломают схему жюри): `type_code`, `confidence`, `end_sec`, `rule {document, clause, url, quote, note}`,

Статусы: `processing` (с `progress: {stage, percent}`), `done`, `failed` (с `error`).
`evidence_frames` — 1–3 JPEG base64, на кадре рамка вокруг зоны/объекта и подпись (код, тип, время).
