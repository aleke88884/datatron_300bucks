# Архитектура решения и используемые модели

Кейс ForteBank (Datathon 26): локальный веб-сервис + API, который по `.mov`-записи кассы выдаёт вердикт
`violation` / `no_violation`, список событий с таймкодом, кадрами-доказательствами и ссылкой на пункт
нормативного акта РК. Этот документ — описание архитектуры и моделей (раздел 8 ТЗ).

Актуальный код: `service/` (пайплайн `service/pipeline/`, API `service/app/`, UI `service/static/`).
Версия пайплайна на момент написания — `0.3.0` (слой восприятия подключён, правила на таблице состояний, VLM-слой как опция).

## 1. Принцип: структурный пайплайн + правила, VLM — не судья

Мы сознательно **не** отдаём видео мультимодальной модели с вопросом «есть ли нарушение?». Такой подход даёт
шумные вердикты, неточные таймкоды и выдуманные ссылки на нормативку, а ТЗ штрафует и ложные срабатывания,
и пропуски. Вместо этого нарушение определяется **состоянием объектов сцены в момент события** (сейф открыт?
деньги на столе? экран активен? кто в помещении?), а таймкод — это **момент перехода состояния**.

Три слоя (ПЛАН §5.1):

```
.mov ──▶ [1] Восприятие ──▶ [2] Сцена и состояния ──▶ [3] Правила T1–T13 ──▶ JSON + кадры
             (3 к/с)            (роли, зоны, булевы        (машина состояний,        │
                                 состояния по секундам)     таймкод = переход)        ▼
                                                                          [4] VLM (локальная, опц.)
                                                                              описание / страховка
```

### Слой 1. Восприятие (по кадрам, 3 к/с)

- Декодирование `.mov` — OpenCV (бэкенд FFmpeg из `imageio-ffmpeg`), `pipeline/video.py`. Отдельно строится
  ряд средней яркости кадра на 10 к/с (для T9 «свет выключен» и T3 в темноте).
- Детектор людей и объектов — **YOLOX-m** (COCO, 80 классов) через **ONNX Runtime**, `pipeline/detect.py`.
  Провайдер берётся из окружения: `ORT_PROVIDERS=CPUExecutionProvider` по умолчанию,
  `CUDAExecutionProvider,CPUExecutionProvider` в GPU-образе (`deploy/Dockerfile.gpu`). Вход 640×640 letterbox. Классы, которые используем: `person`, `handbag`/`backpack`/`suitcase` (сумки),
  `cup`/`bottle`/`wine glass` (напитки), `cell phone`, `laptop`, `chair`, `dining table`.
- Треки людей и признак «внутри кассы» — `pipeline/perception.py`: простое сопоставление рамок между кадрами
  (3 к/с), точка опоры (низ рамки) относительно порога двери и матовой полосы стекла, с гистерезисом.
- Состояния сцены — `pipeline/states.py` (признаки v2): якоря (стол, сейф по нескольким кадрам, ноутбук, полоса
  двери), признаки на 2 к/с: полоса двери, «тёмный проём» у сейфа, экран (активен / заблокирован / выключен),
  предметы на столешнице по принципу «было дерево — стало не дерево» (цвет/насыщенность: купюры, документы),
  зелёная инкассаторская сумка, детекции предметов (стакан, бутылка, сумка), число людей внутри.
- Если весов детектора нет, пайплайн не падает: работают только правила по яркости (T9-контекст, T3 в темноте),
  причина пишется в `meta.perception_error`.

### Слой 2. Сцена и состояния (по секундам) — `pipeline/scene.py`

Роли и зоны строятся **от детекций, а не от пиксельных координат** — это основа устойчивости к другому ракурсу
(критерий 5):

- **Кассир** — самый долгий уверенный трек у стола. **Посетители** — остальные уверенные треки внутри кассы
  (клиент в зоне обслуживания, третий человек — посторонний). **Фантомы** — слабые/мелкие детекции (люди за
  стеклом, отражения) — в подсчётах не участвуют.
- **Рабочая зона** = сторона стола, где находится кассир; зона сейфа = якорь сейфа; дверь = полоса двери.
- Таблица состояний на сетке 2 к/с: `cashier_inside`, `cashier_at_desk`, `cashier_near_safe`, `n_inside`,
  посетители внутри / в рабочей зоне, предметы на столе (купюры, зелёная сумка, напиток), экран активен,
  дверца сейфа, свет.
- Минимальная длительность состояния (1–2 с, константы `*_SEC` в `rules_scene.py`) и гистерезис — защита от
  дрожания детекций.

**Самокалибровка под камеру ролика — `pipeline/camera.py`** (вызывается в `analyze_video` перед построением
сцены, работает и на живом пути, и на кеше признаков):

- **Масштаб сцены.** Пороги в пикселях (площадь предмета на столе, сумки, отступы зоны стола, минимальный рост
  «настоящего» человека) заданы в пикселях эталонного кадра 464×848 и умножаются на масштаб: H/848 для этой
  камеры, по росту людей в кадре (75-й перцентиль высот уверенных рамок) — если он расходится с H/848 вне
  диапазона ×0.5–1.4 (другое разрешение, приближение, альбомный кадр).
- **Экспозиция.** Цветовые маски (дерево стола, зелёная сумка, серый сейф) и пороги яркости экрана (активен /
  заблокирован, светится в темноте) приводятся к эталонной экспозиции: коэффициент = 137.5 / средняя яркость
  кадра без чёрных полей; в пределах разброса обучающих роликов (×0.85–1.18) коррекции нет.
- **Тест «внутри кассы» без координат двери.** Люди за стеклом стоят дальше стола: низ их рамки выше центра
  столешницы более чем на 0.7 роста человека в кадре; у людей внутри — ниже 0.45 роста (между порогами —
  крупная фигура считается внутри, иначе состояние наследуется по треку). Откалиброванная геометрия этой камеры
  (`SceneGeometry`) остаётся, только если согласуется с этим тестом (расхождение ≤ 5 % уверенных наблюдений;
  на 42 роликах датасета в сумме 11 из 8006, максимум 4 %); иначе (зеркальный кадр, другой ракурс) используется
  относительный тест. На 42 роликах офлайн-оценка в принудительном относительном режиме: те же TP 11 / FP 0.
- **Обрывки трека кассира.** Короткий (≤ 3 с) трек «посетителя», который обрывается/начинается в точке, где через
  ≤ 2 с появляется/исчезает кассир, присоединяется к кассиру (при повороте кадра детектор чаще теряет человека).
  Режим и коэффициенты видны в `meta.scene.camera`; переключатель `CAMERA_INSIDE=auto|fixed|relative`.
- Проверка: `scripts/robustness.py` прогоняет живой пайплайн на преобразованных вариантах видео (отражение,
  повороты ±15–20°, перспектива, приближение, экспозиция, альбомный кадр 1280×720), таблица — `results/robustness.md`.

### Слой 3. Правила — машина состояний T1–T13

`pipeline/rules_scene.py` (правила на таблице состояний) и `pipeline/detectors.py` (список `DETECTORS`, T9 и T3
в темноте по яркости). Событие = переход состояния; `timecode_sec` = момент, когда условие стало истинным (для
«нарушений по бездействию» — момент, когда кассир пересёк границу зоны / посетитель вошёл). Для каждого события —
1–3 кадра с рамкой вокруг объекта/зоны и подписью (`pipeline/draw.py`).

Правила делятся на две фазы:
1. **Контекстные** (`CONTEXT_ONLY_TYPES = {"T9"}`) — описывают условия сцены (свет выключен), **не дают вердикт**,
   попадают в `meta.context_events`. Выполняются первыми, их результат видят остальные правила.
2. **Правила-нарушения** — дают события и вердикт.

Политика вердикта (ПЛАН §5.4): `violation`, если есть хотя бы одно событие с `confidence >= 0.5`
(`MIN_CONFIDENCE`). Третьего вердикта нет (ТЗ). Справочник названий, признаков и нормативных пунктов —
`pipeline/rules.py` (см. `RULES_SOURCES.md`, `VIOLATION_TYPES.md`).

Состояние на `0.3.0`:

| Включены | Выключены флагом (`*_ENABLED = False`) — почему | Не реализованы |
|---|---|---|
| T1 (ценности на столе + уход кассира), T3 (экран активен + уход; экран светится в темноте), T4 (третий человек внутри), T5 (посетитель в рабочей зоне), T7 (купюры открыто на столе при входе посетителя), T8 (напиток/еда в зоне стола; личная сумка в руках кассира — `personal_items.py`), T10 (инкассаторская сумка сразу после входа посетителя), T9 — контекст | T2 — признак «тёмный проём у сейфа» растёт и в чистых роликах, когда кассир стоит у сейфа (Х-21, Х-23, Х-25, Х-27); T6 — «предмет на столе» не отличает деньги от документов клиента (ложные Х-5, Х-19); T13 — чистое Х-31 тоже начинается с пустой кассы | T11, T12 — индикаторы «в карман» и «без пересчёта на машинке», нужна поза рук |

Офлайн-оценка по 42 видео (`scripts/eval_rules.py`, кеш признаков из `results/`, 17.10.2026):
**найдено 11 из 22 нарушений, 0 ложных из 20 чистых**, таймкод в пределах 3 с — 7 из 11 (медиана ошибки 2.1 с).
Причины пропусков — `LIMITATIONS.md` §2.

### Слой 4. VLM — только описание и страховка (опционально, локально) — `pipeline/vlm.py`

Локальная мультимодальная модель **Qwen2.5-VL-7B-Instruct** (Apache-2.0) используется **не для вердикта**:
- (а) **описание** (подключено, включается `VLM_ENABLED=1`): по 1–3 кадрам уже найденного события модель
  переписывает шаблон правила в 2–3 предложения «что видно на кадрах». Хук — в `analyze_video` на стадии
  `describing`. Модель не меняет тип, таймкод, уверенность и вердикт; шаблон сохраняется в `description_template`;
  юридические выводы («похитил», «мошенничество») и описания внешности людей отбраковываются постобработкой.
  Лимиты: `VLM_MAX_EVENTS=5`, `VLM_BUDGET_SEC=60`, `VLM_TIMEOUT_SEC=20` — VLM добавляет к видео не более ~60 с,
  лимит ТЗ в 5 минут не нарушается. При любой ошибке/таймауте остаётся шаблон; пайплайн из-за VLM не падает.
- (б) **страховка от неизвестных типов** — метод `checklist` (вопросы «да/нет» по опорным кадрам) реализован,
  но **нигде не вызывается**: по политике ПЛАН §5.4 ответ модели сам по себе событие не добавляет, нужно
  подтверждение детекторами.

Нужен GPU (RTX 3060/4060 с 4-битной загрузкой `VLM_4BIT=1` — 4–8 с на событие; на CPU 7B непригодно медленна).
Без модели (`VLM_ENABLED=0`, нет весов или torch) сервис работает как раньше — описания шаблонные.
Установка: `requirements-vlm.txt`, `scripts/get_vlm.py` (веса ~16 ГБ в `models/vlm/`); подробности —
`service/README.md`, раздел «VLM-слой».

## 2. Модели и лицензии

Все модели — открытые, с лицензиями, разрешающими коммерческое использование. После скачивания весов интернет
не нужен.

| Назначение | Модель | Лицензия | Где в коде / как получить |
|---|---|---|---|
| Детекция людей и объектов | YOLOX-m (COCO), ONNX-экспорт из релиза `Megvii-BaseDetection/YOLOX 0.1.1rc0` | Apache-2.0 | `pipeline/detect.py`; веса `service/models/yolox_m.onnx` (97 МБ) — `scripts/get_models.py`, проверка sha256 |
| Инференс детектора | ONNX Runtime; провайдер из `ORT_PROVIDERS` (CPU по умолчанию, CUDA в `deploy/Dockerfile.gpu`) | MIT | `onnxruntime` в `requirements.txt`, `onnxruntime-gpu` в GPU-образе |
| Декодирование видео | OpenCV + FFmpeg (`imageio-ffmpeg`) | Apache-2.0 / LGPL (ffmpeg) | `pipeline/video.py` |
| Трекинг людей, роли, зоны | собственное сопоставление рамок между кадрами (без внешних весов) | — | `pipeline/perception.py`, `pipeline/scene.py` |
| Состояния сейфа/экрана/стола | эвристики по яркости/цвету/текстуре на кропах (без обучения, признаки v2); план — классификатор кропа дверцы сейфа и детектор купюр по текстуре | — | `pipeline/states.py` |
| VLM: описания событий (опционально, `VLM_ENABLED=1`) | Qwen2.5-VL-7B-Instruct | Apache-2.0 | `pipeline/vlm.py` через transformers (bf16 или 4-bit bitsandbytes); веса `scripts/get_vlm.py` → `models/vlm/` (~16 ГБ); `requirements-vlm.txt`; GPU-образ `deploy/Dockerfile.gpu --build-arg WITH_VLM=1` |

Что **не** используем и почему:
- **Ultralytics YOLO (v5/v8/v11) — AGPL-3.0.** Для коммерческого продукта банка потребовала бы раскрытия кода
  или платной лицензии. Взят YOLOX (Apache-2.0) того же класса качества.
- **Qwen2.5-VL-3B-Instruct — Qwen Research License (некоммерческая).** Берём только 7B (Apache-2.0); `scripts/get_vlm.py` откажется качать 3B без явного флага.
- **Распознавание и идентификация лиц — не используем** (FAQ кейса п. 29). Роли «кассир / клиент / посторонний»
  определяются по положению и трекам в кадре, а не по внешности. Детектор лиц в пайплайне отсутствует.
- Облачные LLM/VLM/API распознавания — не используем; всё выполняется внутри сервиса.

## 3. Локальность и переносимость

- **Локальность.** Сервис — один процесс FastAPI + один воркер-процесс с пайплайном. Никаких внешних вызовов.
  Контейнер проверен с `--network none` (`tests/test_docker.py`). Загруженное видео удаляется сразу после
  анализа (`KEEP_UPLOADS=false` по умолчанию); результаты заданий хранятся только в памяти процесса API.
- **Переносимость.** Зависимости — `requirements.txt` (Python 3.12, OpenCV headless, ONNX Runtime, Pillow).
  Проверен запуск на macOS (Apple Silicon, CPU) и Windows 11 (CPU; `scripts/run_all.ps1` — 9 шагов: Python →
  venv → веса → датасет → признаки → `eval_rules` → pytest → VLM при `WITH_VLM=1` → push). Docker-образ
  `python:3.12-slim` (CPU; веса YOLOX скачиваются на этапе сборки, контейнер работает без интернета) и
  `deploy/Dockerfile.gpu` (NVIDIA CUDA, `onnxruntime-gpu`, опционально VLM). Системный ffmpeg не нужен.
- **Публичный URL** для жюри — туннель к локальному сервису (`deploy/cloudflared.md`) или арендованный GPU-сервер
  с `docker compose`. Туннель только проксирует HTTP; обработка видео остаётся на нашей машине.

## 4. Производительность и лимиты

- ТЗ: ≤ 5 минут на видео. Таймаут воркера — `JOB_TIMEOUT_SEC=240` с запасом; при превышении процесс воркера
  убивается, задание получает `failed`, воркер перезапускается.
- Живой путь с детектором на CPU (Apple M4): 17-секундное видео — **6 с**. Полный сбор признаков на CPU
  (Windows 11, 12 ядер, ONNX Runtime 1.31) для самого длинного видео датасета Х-14 (≈142 с) — ≈125 с, то есть
  ≈1 с на 1 с видео; это верхняя оценка для лимита. Офлайн-оценка по кешу признаков — ~0.3 с на видео.
- VLM-слой (если включён) добавляет не более ~60 с на видео (`VLM_BUDGET_SEC`), на GPU 4–8 с на событие.
- Один воркер, видео обрабатываются по очереди — сознательно: предсказуемые время и память.
- GPU: `ORT_PROVIDERS=CUDAExecutionProvider,CPUExecutionProvider` в `deploy/Dockerfile.gpu` — детектор на CUDA
  (отдельно не замерялось).

## 5. Сервис и API

- `service/app/main.py` — FastAPI; `X-API-Key` на всех `/api/v1/*` (401 без/с неверным ключом); `/health` без ключа.
- `service/app/worker.py` — очередь, один дочерний процесс (`multiprocessing`, spawn), модели загружаются один
  раз в `pipeline.warmup()`.
- `service/static/index.html` — одна страница: загрузка → статус с прогрессом по стадиям → вердикт → события с
  кадрами, описанием, документом + пунктом + ссылкой на adilet, контекст сцены, «Скачать JSON».

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/analyze` | multipart-поле `file` (.mov, до 300 МБ) → `{"job_id": "..."}` (HTTP 202) |
| GET | `/api/v1/jobs/{job_id}` | статус `processing` / `done` / `failed` и результат |
| GET | `/api/v1/rules` | справочник типов нарушений и нормативных пунктов |
| GET | `/health` | без ключа; состояние воркера и очереди |

  "status": "done",
  "verdict": "violation",

      "evidence_frames": [

Поля ТЗ: `job_id`, `status`, `verdict`, `violations[] {type, timecode_sec, description, evidence_frames[] {timestamp_sec, image_base64}}`.
Расширения (не ломают схему жюри): `type_code`, `confidence`, `end_sec`, `rule {document, clause, url, note}`,
`description_template` (шаблон правила, если описание переписала VLM), `meta` (в т. ч. `context_events`, `perception_error`).
Статусы: `processing` (с `progress: {stage, percent}`), `done`, `failed` (с `error`).
`evidence_frames` — 1–3 JPEG base64, на кадре рамка вокруг зоны/объекта и подпись (код, тип, время).

## 6. Что сдаётся вместе с этим документом

- `RULES_SOURCES.md` — нормативные источники и сопоставление «пункт → тип → признак → видео».
- `VIOLATION_TYPES.md` — перечень типов T1–T13.
- `LIMITATIONS.md` — ограничения и известные ошибки.
- `SUBMISSION.md` — пакет сдачи и инструкция по запуску/проверке.
- `service/README.md` — запуск, тесты, переменные окружения.
