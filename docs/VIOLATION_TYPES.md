## Пометки по уверенности и ограничениям

- **T9 — контекст, не нарушение.** Выдаётся только в `meta.context_events`, в `violations` не попадает,
  вердикт не меняет. Используется T3 (экран светится в темноте после ухода кассира).
- **T11 и T12 — индикаторы с повышенным риском ложных срабатываний.** В справочнике помечены `caveat`
  «требует проверки человеком»; в `0.3.0` не реализованы (нужна поза рук), поэтому в ответах API не
  появляются. Сервис не утверждает факт хищения — только фиксирует наблюдаемое движение купюр.
- **T3:** прямого пункта о блокировке сеанса в Правилах № 231 нет; ссылка на п. 14 — общее требование,
  это честно указано в `rule.note`. Вариант «в темноте» не различает, *какое* устройство светится.
- **Выключенные правила (T2, T6, T13)** оставлены в коде с флагами: включать только после
  устранения причины ложных срабатываний на чистых видео — иначе теряем «0 ложных», которое ТЗ ценит больше
  полноты.
- **Неизвестные типы.** Для ситуаций вне T1–T13 в `pipeline/vlm.py` есть метод `checklist` (вопросы «да/нет»
  по опорным кадрам), но он не вызывается: по политике ПЛАН §5.4 событие добавляется только при подтверждении
  детекторами.
- Названия типов — наши; соответствие типам жюри не гарантировано. Точный таймкод (момент перехода состояния)
  и верный вердикт важнее названия.

## Политика вердикта

`violation`, если есть хотя бы одно событие T1–T8, T10–T13 с `confidence ≥ 0.5`; иначе `no_violation`.
Третьего вердикта нет (ТЗ). Таймкод события = момент, когда условие стало истинным (для «нарушений по
бездействию» — момент ухода кассира / появления постороннего), что совпадает с принципом разметки датасета
(таймкод = начало нарушающего действия). На `0.3.0` таймкод в пределах 3 с от разметки — 7 из 11 найденных.
